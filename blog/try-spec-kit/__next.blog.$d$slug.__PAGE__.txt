4:T808b,<h2>写在前面</h2>
<p>这篇文章记录了我把 Spec Kit 引入已有博客项目的一次实践：它帮助我把文章 tags、可见性管理这类增量需求拆解得更清晰，也让我更容易监督和约束 Agent 的产出。</p>
<p>后来我又把 Spec Kit 拿去创建一个<strong>从 0 到 1</strong>的算法游戏项目，这次的体验却没有那么理想：我很难持续跟上 Agent 的产出节奏，最后还是回到了手动开发。</p>
<p>我的最终结论是：Spec Kit 更适合<strong>已有架构、边界清晰</strong>的项目；对于技术栈和产品形态都还没收敛的新项目，它反而可能放大上下文和维护成本。</p>
<h2>什么是 Spec Kit</h2>
<p>Spec Kit 是一个 Spec-Driven Development 开发思想的实践工具，可以把特性开发流程拆得更细。</p>
<p><span data-rehype-pretty-code-figure=""><code data-language="text" data-theme="github-light github-dark"><span data-line=""><span>spec</span></span></code></span> 其实就是 <span data-rehype-pretty-code-figure=""><code data-language="text" data-theme="github-light github-dark"><span data-line=""><span>specification</span></span></code></span>（规格说明）的缩写，翻译过来就是“把需求说详细点”。</p>
<p>Spec-Driven Development 的核心在于把以往<strong>代码优先于说明</strong>的顺序反过来：先尽可能细化需求描述，再进入实现阶段，从而让代码更贴近预期。</p>

<h2>主要流程</h2>
<img src="/img/speckit-0911/speckit-workflow.png" alt="spec-kit 流程图" style="margin: 0 auto; width: 60%;" />
<p>Spec Kit 一般按以下步骤执行：</p>
<ol>
<li>首先要通过 constitution 初始化项目</li>
<li>然后用 specify 命令增加需求</li>
<li>接着用 clarify 帮助 Agent 澄清本次新增特性的疑惑点；</li>
<li>Agent 随后用 plan 命令创建实施计划</li>
<li>再用 tasks 列出细致的实现细节</li>
<li>最后运行 implement 命令按照 tasks 中的步骤实现功能</li>
</ol>
<h3>1. constitution</h3>
<p><span data-rehype-pretty-code-figure=""><code data-language="text" data-theme="github-light github-dark"><span data-line=""><span>constitution</span></span></code></span> 直译为宪章，将 spec 引入项目的时候运行一次即可，它会描述这个项目的用途和开发规则，方便后续开发时进行参考</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="markdown" data-theme="github-light github-dark"><code data-language="markdown" data-theme="github-light github-dark" style="display: grid;"><span data-line=""><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">/speckit.constitution 这是一个网页游戏应用，应当保持代码整洁，核心代码要有注释提示</span></span></code></pre></figure>
<p>这一步会产出一个 <span data-rehype-pretty-code-figure=""><code data-language="text" data-theme="github-light github-dark"><span data-line=""><span>constitution.md</span></span></code></span> 文件，定义在 <span data-rehype-pretty-code-figure=""><code data-language="text" data-theme="github-light github-dark"><span data-line=""><span>.specify/memory/constitution.md</span></span></code></span>。既可以通过 Spec Kit 的 skill 更新，也可以直接让 Agent 去更新这个文件。</p>
<p>第一次用 Spec Kit 的时候，我选择了 Cursor 作为我的 AI assistant，所以它还额外在 <span data-rehype-pretty-code-figure=""><code data-language="text" data-theme="github-light github-dark"><span data-line=""><span>.cursor</span></span></code></span> 文件夹下增加了相关的配置文件</p>
<ul>
<li><span data-rehype-pretty-code-figure=""><code data-language="text" data-theme="github-light github-dark"><span data-line=""><span>.cursor/commands</span></span></code></span>：这个文件夹下包含了 cursor Agent 的命令，比如 <span data-rehype-pretty-code-figure=""><code data-language="text" data-theme="github-light github-dark"><span data-line=""><span>/speckit</span></span></code></span>、<span data-rehype-pretty-code-figure=""><code data-language="text" data-theme="github-light github-dark"><span data-line=""><span>/speckit.specify</span></span></code></span>、<span data-rehype-pretty-code-figure=""><code data-language="text" data-theme="github-light github-dark"><span data-line=""><span>/speckit.clarify</span></span></code></span> 等等</li>
<li><span data-rehype-pretty-code-figure=""><code data-language="text" data-theme="github-light github-dark"><span data-line=""><span>.cursor/rules</span></span></code></span>：这个文件夹下增加了一个 <span data-rehype-pretty-code-figure=""><code data-language="text" data-theme="github-light github-dark"><span data-line=""><span>specify-rules.mdc</span></span></code></span> 文件，有个 <span data-rehype-pretty-code-figure=""><code data-language="text" data-theme="github-light github-dark"><span data-line=""><span>Recent-changes</span></span></code></span> 模块会记录每次 spec-kit 模式添加的特性</li>
</ul>
<p>命令太长了不好记也没关系，输入框中输入 <span data-rehype-pretty-code-figure=""><code data-language="text" data-theme="github-light github-dark"><span data-line=""><span>/speckit.constitution</span></span></code></span>，等待 Agent 自动补全 command 字段就行。</p>
<p>这一步相当于给整个项目<strong>打地基</strong>，它告诉 Spec Kit 这个项目的用途和预期形态。</p>
<p>我这里写得很简略，但实际使用时完全可以补充更多信息，比如它是否是静态项目、是否需要连接数据库等，方便 Spec Kit 在后续决策中依赖 <span data-rehype-pretty-code-figure=""><code data-language="text" data-theme="github-light github-dark"><span data-line=""><span>constitution</span></span></code></span> 做判断。</p>
<h3>2. specify</h3>
<p>这一步就开始加特性了，写上你想要新增的需求，包括 what 和 why。</p>
<p>对于从 0 开始的算法游戏项目，我写得比较宽泛，因为我也不确定第一个特性要怎么加，所以就先把网站的用途和面向的用户群体写了下来。</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="markdown" data-theme="github-light github-dark"><code data-language="markdown" data-theme="github-light github-dark" style="display: grid;"><span data-line=""><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">/speckit.specify 创建一个基础的 web 小游戏应用平台，主要用途为娱乐、教育、儿童友好，方便我在开发过程中熟悉基础算法知识</span></span></code></pre></figure>
<p>对于已经建好的博客网站，我就写得更具体一些，因为这个 tag 特性我已经大致知道要做成什么样子。</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="markdown" data-theme="github-light github-dark"><code data-language="markdown" data-theme="github-light github-dark" style="display: grid;"><span data-line=""><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">/speckit.specify 我想要让博客文章支持 tags 功能，每个文章应该会有至少一个 tag，可以包含多个，用户可以通过 tag 路由：</span><span style="--shiki-light:#005CC5;--shiki-dark:#79B8FF">`/tags/spec/`</span><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8"> 访问包含该 tag 的所有文章，方便用户访问特定种类的文章</span></span></code></pre></figure>
<p><strong>看 Spec Kit 怎么处理的？</strong></p>
<ul>
<li>首先，<strong>自动切换到一个新的分支</strong>。以博客项目为例，加 tag 特性时会自动切到 <span data-rehype-pretty-code-figure=""><code data-language="text" data-theme="github-light github-dark"><span data-line=""><span>001-blog-post-tags</span></span></code></span>。
<ul>
<li>这是个我认为<strong>特别加分</strong>的特性。自己开发时很容易忘记切分支，结果直接在主分支上持续迭代。</li>
</ul>
</li>
<li>然后在 <span data-rehype-pretty-code-figure=""><code data-language="text" data-theme="github-light github-dark"><span data-line=""><span>specs</span></span></code></span> 目录下为这个特性创建专属文件夹（游戏平台项目里对应的是 <span data-rehype-pretty-code-figure=""><code data-language="text" data-theme="github-light github-dark"><span data-line=""><span>001-web-game-platform</span></span></code></span>），里头有详细的需求文档和 checklist：
<ul>
<li>需求文档 spec.md 很详细，有 user stories 和 edge cases</li>
</ul>
</li>
</ul>
<p><span data-rehype-pretty-code-figure=""><code data-language="text" data-theme="github-light github-dark"><span data-line=""><span>specify</span></span></code></span> 这一步是需求开发的起点。把自己想要的特性描述清楚，能明显提升 Agent 生成代码的质量。</p>
<h3>3. clarify</h3>
<p>我认为 <span data-rehype-pretty-code-figure=""><code data-language="text" data-theme="github-light github-dark"><span data-line=""><span>clarify</span></span></code></span> 是 Spec Kit 很有价值的一个环节，它会继续检查上一步里哪些功能还不够清晰。这个过程中，Agent 会逐个列出不明确的点，并通过提供选项问你要按什么方式去实现。</p>
<p>虽然我们平常开发也可以通过提示词让 AI 在修改前反问，以此搞清楚变动方向，但远没有这么细致。</p>
<p>我在开发过程中想不出来 <span data-rehype-pretty-code-figure=""><code data-language="text" data-theme="github-light github-dark"><span data-line=""><span>clarify</span></span></code></span> 要写什么，就直接跑了命令，让 Agent 自己分析还有什么问题。</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="markdown" data-theme="github-light github-dark"><code data-language="markdown" data-theme="github-light github-dark" style="display: grid;"><span data-line=""><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">/speckit.clarify</span></span></code></pre></figure>
<p>开发网页游戏项目的时候，Agent 只问了一个问题，并更新了上一轮中的 <span data-rehype-pretty-code-figure=""><code data-language="text" data-theme="github-light github-dark"><span data-line=""><span>spec.md</span></span></code></span> 文件，写入 <span data-rehype-pretty-code-figure=""><code data-language="text" data-theme="github-light github-dark"><span data-line=""><span>## Clarifications</span></span></code></span> 中。</p>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="markdown" data-theme="github-light github-dark"><code data-language="markdown" data-theme="github-light github-dark" style="display: grid;"><span data-line=""><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">Q: 首个内置小游戏（MVP）希望主打哪个算法主题？ → A: 迷宫寻路</span></span></code></pre></figure>
<p>在我的博客网站中实现 tag 特性时，它问得反而更多。</p>
<ul>
<li>我理解这是因为新项目本身限制不多，Agent 只需要一个相对模糊的需求就能开始推进，它的决策空间也更大；</li>
<li>但在已有项目里，架构和技术栈都已经定型，Agent 的改动会受到更多约束，所以才会主动要求更多澄清。</li>
</ul>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="markdown" data-theme="github-light github-dark"><code data-language="markdown" data-theme="github-light github-dark" style="display: grid;"><span data-line=""><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">澄清问题 1 / 最多 5 个</span></span>
<span data-line=""><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">背景： Edge Cases 里写了「无文章时仍访问标签地址 → 空列表」；但未说明：从未在任何文章中出现过的 tag slug（例如拼写错误、乱打的 /tags/xyz/）是否与「有 tag、但暂时 0 篇」表现一致。</span></span>
<span data-line=""> </span>
<span data-line=""><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">推荐：选项 A — 与「该标签下暂无文章」一致，统一为 200 + 空列表 + 简短说明。静态博客里不必区分「库里没有这个 tag」和「有这个 tag 但列表为空」，实现和测试都更简单，也和当前「默认不用误导性错误页」一致。</span></span></code></pre></figure>
<h3>4. plan</h3>
<p>这一步就开始落实到具体实现。之前跟 Agent 交流的时候，我简单说过想<strong>用什么技术栈来实现</strong>，它却直接回绝，表示这些内容应该写在 <span data-rehype-pretty-code-figure=""><code data-language="text" data-theme="github-light github-dark"><span data-line=""><span>plan</span></span></code></span> 中。</p>
<p>实际做需求时，也不该先看“我们手里有什么技术栈、它能做什么”，而是反过来让技术为需求服务：先明确需求，再判断当前技术是否足以支撑。我觉得这样的规划更合理。</p>
<blockquote>
<p>你额外提到“用 HTML Canvas 实现游戏、Naive UI 作为组件库”。这是实现方案层面的约束，我不会写进 spec（避免让 spec 变成实现文档），我会在下一步 /speckit-plan 的技术方案里落实。</p>
</blockquote>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="markdown" data-theme="github-light github-dark"><code data-language="markdown" data-theme="github-light github-dark" style="display: grid;"><span data-line=""><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">/speckit.plan 用 Canvas 实现游戏界面，Naive UI 作为项目的组件库</span></span></code></pre></figure>
<p>可以看到，这个步骤的具体产物有这些：</p>
<ul>
<li>计划文件，描述本次的特性总结和产出文件大纲： plan.md</li>
<li>研究结论，本次具体要实现的产物和技术栈选项： research.md</li>
<li>数据模型： data-model.md</li>
<li>运行验证，最小验证工作流： quickstart.md</li>
<li>合同（内部模块契约）： contracts/game-module.md， contracts/maze-pathfinding.md</li>
</ul>
<h3>5. tasks</h3>
<p>前面的步骤都有些抽象，而 <span data-rehype-pretty-code-figure=""><code data-language="text" data-theme="github-light github-dark"><span data-line=""><span>tasks</span></span></code></span> 这一步会根据之前的产物生成一份非常详细、可直接执行的任务拆解清单。</p>
<p><span data-rehype-pretty-code-figure=""><code data-language="text" data-theme="github-light github-dark"><span data-line=""><span>tasks</span></span></code></span> 命令我认为也是 Spec Kit 的核心命令。它非常贴近日常研发工作，本质上是在把相对抽象的需求特性翻译成具体可执行的 checklist，再逐项落地。</p>
<p>这一步生成的任务拆解清单 <span data-rehype-pretty-code-figure=""><code data-language="text" data-theme="github-light github-dark"><span data-line=""><span>tasks.md</span></span></code></span> 内容如下：</p>
<ol>
<li><strong>前置检查</strong>：是否<strong>已切换了分支</strong>，并盘点影响的文件。</li>
</ol>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="markdown" data-theme="github-light github-dark"><code data-language="markdown" data-theme="github-light github-dark" style="display: grid;"><span data-line=""><span style="--shiki-light:#24292E;--shiki-light-font-weight:bold;--shiki-dark:#E1E4E8;--shiki-dark-font-weight:bold">**Prerequisites**</span><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">: plan.md (required), spec.md (required), research.md, data-model.md, contracts/, quickstart.md</span></span></code></pre></figure>
<ol start="2">
<li>接着是<strong>任务清单</strong>本身，记录了每个文件的具体改动，比 Plan 阶段的描述更细，甚至能精确到文件里的方法。</li>
</ol>
<ul>
<li>比如要安装额外依赖、在指定位置创建文件夹，这些都是我们作为研发需要重点复核和斟酌的部分。</li>
<li>对于算法游戏，因为是初始化项目，所以 <span data-rehype-pretty-code-figure=""><code data-language="text" data-theme="github-light github-dark"><span data-line=""><span>tasks.md</span></span></code></span> 里还会包含多个 phase 逐步演进。</li>
<li>博客网站项目就相对简单一些。</li>
</ul>
<figure data-rehype-pretty-code-figure=""><pre tabindex="0" data-language="markdown" data-theme="github-light github-dark"><code data-language="markdown" data-theme="github-light github-dark" style="display: grid;"><span data-line=""><span style="--shiki-light:#005CC5;--shiki-light-font-weight:bold;--shiki-dark:#79B8FF;--shiki-dark-font-weight:bold">## Phase 1: Setup (Shared Infrastructure)</span></span>
<span data-line=""> </span>

<h2>总结</h2>
<p>开头的时候我也说过，我认为 Spec Kit 对已有项目，也就是项目架构和技术栈都已经确定的项目，贴合度会更高；对于从 0 到 1 的新项目，用起来则更容易失去掌控。</p>
<ul>
<li>初始化阶段的<strong>技术栈选型、状态管理</strong>往往都还没有稳定下来，这时候一下子生成大量文件和代码，理解成本与维护成本都会迅速上升。</li>
<li>如果习惯了 Vibe coding的节奏, 本来就接受较高的不确定性，这套流程的约束价值可能没那么明显；但对专业开发来说，能否<strong>持续掌控 Agent 的产出</strong>依然是很重要的前提。</li>
</ul>
<p>再说下 Spec Kit 的工作流程。</p>
<ol>
<li>在实现特性的步骤中<strong>自动切换分支</strong>，这一点确实很方便。</li>
<li><span data-rehype-pretty-code-figure=""><code data-language="text" data-theme="github-light github-dark"><span data-line=""><span>/clarify</span></span></code></span> 这个命令非常加分。开发时如果 Agent 在特性边界不清楚的情况下就直接动手改，很容易产出后续维护成本较高的代码，最后还得开发者自己收尾。</li>
<li>每个步骤都会<strong>产出一大堆文件</strong>，这是它的优点也是缺点</li>
</ol>
<ul>
<li>这些文件确实能帮助梳理需求，特别是对于复杂特性，checklist 能保证没有遗漏关键的 edge case。</li>
<li>比如我增加 tag 功能时，Agent 会帮我梳理出哪些路由需要增加、哪些文件需要修改、哪些测试用例需要补、哪些文档需要同步，而且这些文件都是模板化的，可以复用，所以不会平白增加太多工作量。</li>
<li>但它的代价也很明确。现在的主流思路通常是尽量<strong>压缩上下文</strong>，而 Spec Kit 反过来要求你保留更多过程文档，这意味着更高的 token 开销，也意味着更多阅读和维护成本。</li>
<li>所以我的判断是：对于复杂特性，这种约束和文档化是值得的；但对于很小的特性，它就会显得偏重。</li>
</ul>
